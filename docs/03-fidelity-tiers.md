# Fidelity tiers — how much realism the job actually needs

"Synthetic data" covers four quite different things. They cost different amounts, catch different bugs, and most projects need more than one of them at once. Building tier 3 when tier 0 would do is the most common way to waste a month.

| Tier | What it is | Validates | Cost |
|---|---|---|---|
| **0** | Hand-built fixtures, inline in the test file | One rule, one function | Minutes |
| **1** | Schema-faithful file mirror | The cleaning pipeline | Days to a week |
| **2** | Tier 1 + an encoded data-generating process | The analysis code | + days |
| **3** | Tier 2 + calibrated to real moments | Volumes, rates, distributions | + an enclave round trip |

---

## Tier 0 — hand-built fixtures

A dozen rows, constructed by hand in the test file, with the answer written next to them. No data files, no generator, no directory structure.

```r
# Person 1 is discharged 2018-03-10 and readmitted 2018-03-25 -> 30-day readmit
# Person 2 is discharged 2018-03-10 and readmitted 2018-05-01 -> not a readmit
```

**Use it for:** the logic of a single rule — an event window, a spell-collapsing routine, a waterfall of date evidence, a treatment-status classifier. Anything where you can state the expected output in one line.

**Do not skip this tier because you have tier 1.** They catch different things. A schema mirror tells you the pipeline runs; a fixture tells you a specific rule is correct. When an event-study builder has thirty edge cases around window boundaries and spell trimming, thirty fixtures are the right tool and a synthetic claims file is the wrong one.

**Tell:** if your test needs a data file to run, it is probably testing too much at once.

---

## Tier 1 — schema-faithful file mirror

The real files, in the real shapes, with the real column names, containing random values and injected defects. This is what [02-the-blueprint.md](02-the-blueprint.md) mostly describes, and what a tier-1 generator builds.

**Use it for:** every project that has to write nontrivial cleaning code against restricted files. This is the workhorse tier.

**Deliberately not realistic.** Volumes, rates, and distributions are whatever is convenient. Aim for **coverage, not realism** — the random portion exists to exercise the common paths by volume, scenarios exercise the corner cases, and injections exercise the cleaner. Realism in the random portion is a third-order concern that tier 3 addresses later, if ever.

**Tell that you need it:** you are about to write a reshape, a join across file segments, or a defect-handling branch, and you cannot run it without enclave access.

---

## Tier 2 — encoded data-generating process

Tier 1, plus outcomes generated by a process with a **known true effect**, recorded in a truth file the analysis code never reads.

**Use it for:** validating estimators. Event studies, difference-in-differences, staggered adoption with heterogeneous effects, spillover specifications, anything with a comparison group.

**Why it earns its cost:** cleaning bugs usually announce themselves — a merge rate collapses, an assertion fires, a row count is absurd. Analysis bugs do not. A difference-in-differences at the wrong unit of analysis runs perfectly and returns a plausible, significant, correctly-signed number. On real data there is nothing to check it against.

That failure is worth seeing concretely: the same estimator on an enrolled bene-month panel and on a panel built from the claims file, where the months with no claim are missing. Nothing about the wrong run looks wrong.

**Scope it.** You do not need a realistic DGP for the whole dataset — only for the outcome and the treatment your headline specification uses. Everything else can stay tier 1.

**The limit, and it is a real one:** the generator makes its own assumptions true. If treated and control units are drawn from the same process until the shock date, parallel trends holds by construction. Recovering the encoded effect proves the estimator works on data satisfying its assumptions. It says nothing about whether real data satisfies them.

---

## Tier 3 — calibrated to real moments

Tier 2, with parameters set from suppression-compliant aggregates exported from the enclave. See [06-calibration-loop.md](06-calibration-loop.md).

**Use it when:** the *magnitude* of something matters for a decision — whether a sample restriction leaves enough power, whether a rare outcome is common enough to study, whether one state's fill rate makes it unusable. Also when you are handing the synthetic data to someone who will form intuitions from it.

**Skip it when:** you only need the pipeline to run correctly. Most projects never need tier 3, and reaching for it early is a way to spend a month on precision that changes no decision.

**Requires enclave access already.** It is a feedback loop, so it cannot be the thing you do first. Build tiers 1 and 2, port to the enclave, then calibrate.

**Expect the first pass to be embarrassing, and let it be.** On one project here, the first calibration run found the embedded utilization effect at +53% and +98% against a design of +20% and +10% — the baseline rates for the comparison arm had been set far too low. That is the loop working: a wrong number that had been sitting in the generator for weeks became visible the moment there was something to compare it to. If your first calibration run matches everything, be suspicious of the moments rather than pleased with the generator.

---

## Choosing

Most projects run **tier 0 alongside tier 1**, add **tier 2** when the headline specification stabilizes, and reach **tier 3** only if a magnitude question forces it.

| If you are... | Build |
|---|---|
| Writing a tricky rule with edge cases | Tier 0 |
| Writing a cleaning pipeline before you have access | Tier 1 |
| Writing an event study or DiD | Tier 2 for the outcome and treatment |
| Deciding whether a sample is large enough to study | Tier 3 for the relevant rates |
| Onboarding an RA who has no access yet | Tier 1, plus whatever tier 0 fixtures their task needs |
| Doing a handful of tabulations from one clean file | None — write it in the enclave |
